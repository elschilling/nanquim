## Purpose

Nanquim already has a broad pre-1.0 feature set. The next goal is to make a
complete technical-drawing workflow trustworthy, testable, teachable, and
releasable before expanding the command catalog.

The target sequence is:

```text
Repository truth
      -> Safe documents
      -> Predictable editing
      -> Qualified Paper Space and file exchange
      -> Onboarding and tutorials
      -> Public beta
      -> Feedback-driven features
```

This document is the active implementation roadmap. Superseded roadmap drafts
were consolidated here and removed from the working tree because they described
several delivered features as missing. Their historical context remains
available in Git history.

## Planning assumptions

- Reliability has priority over adding commands.
- Estimates assume one developer working on one primary engineering track at a
  time. Part-time work may take two to three times longer.
- Milestone dates are not commitments. Each phase ends when its acceptance
  criteria pass.
- Application versions and saved-document schema versions are independent.
- Persistent serialized Undo history is not beta scope; New/Open should reset
  history safely.
- Refactoring follows characterization tests; large modules are not rewritten
  speculatively.
- Every user-visible capability should eventually have tests, Help metadata,
  written documentation, and a content-impact decision.

## Current baseline

As of the review date:

- 30 terminal commands are registered in `src/js/commands/_commands.js`.
- Searchable F1 Help covers every command and includes one inline SVG diagram
  per command.
- The automated suite has 168 passing tests across 17 files.
- CI runs a frozen install, tests, production build, and high-severity
  dependency audit.
- Native saves emit document schema v2, historical project samples used schema
  v1, and Geometry Nodes uses its own schema v1. Small, purpose-built licensed
  v1/v2 SVG and DXF parser fixtures now establish Phase 1 characterization
  baselines; they do not yet prove complete save/reopen compatibility.
- Model Space, Paper Space, collections, blocks, SVG/DXF I/O, PDF output, and
  experimental Geometry Nodes are implemented.
- The published beta matrix makes desktop Chromium the primary target, Firefox
  the supported upload/download-fallback target, and Safari/WebKit best-effort
  with a manual prerelease check until automated coverage exists.

Important gaps discovered during the roadmap audit:

- The current save path appears to omit editable Paper Space annotations and
  imported SVG definitions other than block definitions. Regression tests must
  prove the exact loss cases before the serializer is changed.
- Open/New does not have one documented reset path for selection, active
  interaction state, managers, file handles, and Undo/Redo history.
- Some drawing commands write directly to `history.undos`, bypassing normal
  execution and redo-branch invalidation.
- Most CAD command workflows do not yet have lifecycle-level tests.
- There is no automated real-browser suite or coverage report.
- `master` is now the documented canonical branch, GitHub's verified default,
  CI target, Vercel production branch, and local `origin/HEAD`. An active GitHub
  ruleset protects it, and the obsolete `svgcad` Vercel project has been
  removed.
- The package and build use `0.1.0-alpha.1`, with a changelog and prepared
  release notes. The matching commit, tag, and GitHub prerelease do not exist
  until Phase 0 is reviewed and publishing is explicitly authorized.
- Mixed SVG.js runtimes, mixed static/dynamic imports, the large main chunk, and
  large coupled modules remain technical debt.

## Phase 1 - Safe documents

Status: Not started.

Dependencies: Phase 0 version and repository decisions.

### 1. Characterize the current document format

Before refactoring, create fixtures and failing tests for:

- Model collections and nested groups.
- Specialized arc, circle-trim, spline, hatch, and dimension metadata.
- Text and dimension styles.
- Blocks, definitions, instances, and internal references.
- Imported gradients, patterns, masks, clip paths, markers, symbols, and styles.
- Paper settings, viewports, and editable Paper annotations.
- Geometry Nodes graphs, instances, source ownership, and cached output.
- Native document schema v1 and v2 fixtures, plus Geometry Nodes schema v1.
- Text, collection/style names, block names, and metadata containing XML-special
  characters and both quote styles.

### 2. Introduce a canonical document serializer

Create one serialization boundary responsible for the entire editable document.
Saving from the navbar, direct file handles, downloads, tests, and future crash
recovery must use the same serializer.

The serializer must:

- Preserve semantic SVG rather than merely visible pixels.
- Preserve valid IDs and internal references without collisions.
- Include imported definitions and Paper annotations.
- Serialize collection, style, block, viewport, and Geometry Nodes state.
- Avoid interaction-only classes, helpers, handles, and transient selections.
- Escape text and attribute contexts correctly. Prefer structured XML/DOM
  serialization over ad hoc string replacement for names and metadata.
- Produce deterministic enough output for semantic comparisons.

### 3. Validate and migrate schema versions

- Parse and validate the saved document version.
- Add deterministic v1-to-current and v2-to-current fixtures and keep Geometry
  Nodes schema migration independent.
- Bound JSON size, depth, node count, and numeric ranges.
- Isolate invalid metadata while preserving safe geometry where possible.
- Decide whether a future-schema document is rejected before Open or presented
  through an explicit read-only mode. In either case it must not mutate the
  current document, be silently downgraded, or become writable as the current
  schema.
- Surface clear messages for migrated, partially recovered, and unsupported
  documents.

### 4. Add a complete document lifecycle

- Implement explicit New, Open, Save, and Save As behavior.
- Stage parsing, migration, sanitization, hydration, and manager loading before
  atomically replacing the live session. Any failure must preserve the previous
  document, dirty state, history, and file handle.
- Centralize reset of selection, commands, helpers, managers, collections,
  spatial indexes, file handles, and history.
- Track dirty/saved state from document mutations.
- Define native Save/Save As as lossless editable-document operations. Move
  white-to-black conversion and other presentation changes into explicit Export
  actions; exports do not clear dirty state or replace the native file handle.
- Warn before losing unsaved work through New, Open, reload, or tab close.
- Ensure fallback upload/download behavior cannot overwrite the wrong file.
- Keep persistent recent-file handles optional and permission-aware.

### Acceptance criteria

- A canonical document containing every supported subsystem survives
  `create -> save -> reopen -> save` without semantic loss.
- Paper annotations and imported definitions persist and render correctly.
- New/Open always starts with empty history and neutral interaction state.
- Undo from one document can never mutate another document.
- Corrupt metadata produces a bounded warning rather than a crash or unsafe
  document rewrite.
- A future-schema fixture follows the chosen reject/read-only policy without
  changing or downgrading the active document.
- A failure at any Open stage leaves the prior document, history, dirty state,
  and file handle intact.
- Save marks the session clean only after a successful disk write. Cancellation
  and write failure preserve dirty state and the previous handle.
- Export transformations do not change the editable document or native handle.
- XML-special characters in names, text, and metadata survive safely and
  exactly through the semantic round trip.
- Direct-handle and download/upload workflows have equivalent saved content.

## Phase 2 - Predictable editing

Status: Not started.

Dependencies: Stable document reset and representative fixtures from Phase 1.
The coverage and browser-harness scaffolding may begin in parallel during Phase
1 as long as tests do not encode unsafe lifecycle behavior.

### 1. Add coverage and a deterministic test harness

- Add Vitest coverage for application code while excluding vendored libraries.
- Record the initial baseline and ratchet thresholds upward.
- Give new or substantially changed modules a higher local threshold.
- Provide shared Editor, SVG, signal, terminal, collection, clipboard, timer,
  animation-frame, and file API fixtures.
- Detect leaked listeners, subscriptions, timers, helpers, and interaction flags.

### 2. Define a lifecycle contract for all registered commands

Each command must verify, where applicable:

- Canonical name, aliases, category, and Help metadata.
- Pointer and typed input paths.
- Result geometry and specialized metadata.
- Active collection and inherited style.
- Preview/helper visibility and cleanup.
- Terminal prompts and recording of typed values.
- Escape, invalid input, and repeated cancellation.
- Selection, UI signals, and spatial-index invalidation.
- Undo and Redo against normalized document state.
- Model Space versus Paper Space availability.

Prioritize in this order:

1. Trim, Extend, Fillet, Offset, and their intersection helpers.
2. Move, Copy, Rotate, Scale, Mirror, and transformed geometry.
3. Snaps on arcs, ellipse arcs, splines, nested groups, and block instances.
4. Drawing and annotation commands.
5. Blocks, viewports, and Geometry Nodes mutations.

### 3. Make mutations transactional

- Route new and changed mutations through one History execution path.
- Stop adding new direct writes to `history.undos` or `history.redos`.
- Migrate existing direct writes behind regression coverage.
- Clear the redo branch after a new edit.
- Define transaction boundaries for multi-step commands.
- Document history behavior for Properties, collections, Paper Space, Blocks,
  and Geometry Nodes.

### 4. Centralize command invocation and cancellation

- Resolve command names and aliases through one runner.
- Give command sessions an explicit cleanup/disposal contract.
- Return the editor to a neutral state after completion, error, or Escape.
- Prevent orphan previews and duplicated signal subscriptions.
- Keep terminal, toolbar, keyboard, and future Help actions behaviorally
  equivalent.

### 5. Add real-browser workflow tests

Use an open-source browser harness such as Playwright.

Run current Chromium smoke tests on each pull request and current Firefox on a
scheduled or prerelease job. Run a documented Safari/WebKit manual smoke check
before beta candidates while it remains best-effort. Preserve traces, console
logs, and screenshots on automated failure.

Minimum browser flows:

- Create a rectangle using typed dimensions.
- Select, Move, Undo, and Redo.
- Cancel an active command without leaving helpers.
- Save and reopen a representative SVG.
- Copy and paste sanitized geometry.
- Create and export a Paper viewport.
- Open, search, and keyboard-navigate Help.
- Load and evaluate a Geometry Nodes example.

### Acceptance criteria

- Every registered command has at least one lifecycle contract.
- High-risk geometry combinations have explicit supported/unsupported results.
- Repeated start/cancel cycles leave stable listener and helper counts.
- Undo/Redo round trips reproduce normalized document state.
- Core workflows pass in the browser versions named in the published beta
  support matrix without uncaught exceptions.
- CI stores actionable browser artifacts for failures.

## Phase 3 - Qualify Paper Space and file exchange

Status: Not started.

Dependencies: Canonical serializer, command contracts, and browser harness.

### 1. Finish production Paper Space

- Persist annotations and all viewport state, including locking and visibility.
- Make viewport locking functional and durable.
- Verify scale presets, model origins, and ISO A0-A4 dimensions.
- Preview color mappings accurately and preserve ordinary SVG stroke widths.
- Make an explicit scope decision before adding per-color plot-lineweight
  mapping; it is not assumed to be an existing beta feature.
- Verify local font embedding and dimension readability.
- Preserve vector output in standalone SVG and PDF.
- Decide whether multi-sheet documents are pre-1.0 scope. The default proposal
  is one reliable sheet for the first beta.

### 2. Build an interoperability qualification suite

Curate small fixtures for primitives, arcs, ellipses, polylines, splines, text,
collections, blocks, transforms, hatches, Paper Space, and unsupported entities.

Check semantic results against:

- Browsers and Inkscape for SVG.
- A pinned LibreCAD version for DXF. QCAD Community may be an additional manual
  target only when its exact version is recorded.
- A pinned Blender version for the first SVG interoperability profile.

Compare entity counts, bounds, units, collections/layers, styles, and internal
references within documented tolerances. Report skipped or degraded entities to
the user rather than silently dropping them.

### 3. Establish performance budgets

Create fixed 1,000- and 10,000-element drawings and measure:

- Load and save.
- Spatial-index rebuild and queries.
- Pan, zoom, window selection, and snapping.
- Outliner rendering and synchronization.
- Geometry Nodes evaluation.

Record median and upper-percentile timings with tolerant regression budgets.
Optimize only after a behavior and performance baseline exists.

### Acceptance criteria

- Paper fixtures export at correct physical sizes and viewport scales.
- Color, existing stroke-width, font, dimension, and vector-output checks pass.
- Supported SVG/DXF entities preserve documented semantics and tolerances.
- Unsupported entities generate an understandable summary.
- Test fixtures are not present in production output.
- Performance regressions are measurable before optimization begins.

## Phase 4 - Onboarding, documentation, and tutorials

Status: Not started.

Dependencies: A tagged, stable workflow from Phases 1-3. Documentation work can

### 1. Build task-based documentation


- Keep README as the landing page.
- Generate or validate command reference data against the command registry.
- Extend command metadata with syntax, ordered steps, options, examples, and
  supported editor contexts.
- Reuse the Help illustration grammar in written guides and video callouts.
- Mark Geometry Nodes and other unstable features as experimental.
- Add tested-version information to task tutorials.

### 2. Improve first-run onboarding

- Add Open Example and First Drawing Guide actions to the Welcome screen.
- Provide small, licensed starter and completed drawings.
- Add a dismissible checklist for pan/zoom, Rectangle dimensions, snaps, Undo,
  Save, and F1 Help.
- Make the application version and experimental status visible.
- Keep onboarding keyboard accessible and independent of persistent file APIs.

### 3. Create a repeatable Fedora/FOSS content workflow

- OBS Studio: capture to MKV, then remux for editing.
- Blender Video Sequence Editor: editing, crops, transitions, and text strips.
- Inkscape: SVG thumbnails and title cards.
- FFmpeg: inspection and final encoding.
- Captions: concise burned-in instructional text plus an equivalent `.srt`.

Use 1920x1080 at 30 fps unless testing demonstrates a better target. Verify
terminal text, cursor, snap markers, helpers, and dimensions at YouTube's 720p
playback size. Keep rendered video and large `.blend` files outside the
application repository.

### 4. Publish a starter batch

Publish three caption-first videos before broadly announcing the channel:

1. **Nanquim: Browser-Based SVG CAD in Two Minutes**
2. **Your First Precise Drawing**
3. **Terminal, Coordinates, Ortho, and Snaps**

Each episode requires a storyboard, versioned sample, captions, thumbnail,
chapters, description, tested application version, limitations, and links to
the demo, source, written guide, and issue tracker.

Continue with selection/editing, curves, collections, annotation, Blocks,
interoperability, Paper Space, and Geometry Nodes at a sustainable cadence of
one four-to-eight-minute tutorial every one or two weeks. Keep two completed
episodes in reserve when possible.

### Acceptance criteria

- In a clean browser profile, at least three first-time participants can follow
  only the published guide to create, dimension, save, close, and reopen the
  sample; all complete it and the median completion time is under ten minutes.
- Help and the written command reference cannot drift silently.
- Onboarding is dismissible, restartable, keyboard accessible, and works with
  browser file fallbacks.
- Every episode can be reproduced from its tagged sample and written guide.
- Captions remain complete and readable when watched muted at 720p.
- User-facing changes receive a docs/Help/video impact decision.

## Phase 5 - Public beta and feedback

Status: Not started.

Dependencies: Exit criteria from Phases 0-4 for the supported beta surface.

### Release deliverables

- Tag and publish `v0.1.0-beta.1` with a changelog, compatibility notes, and
  known limitations. Promote to `v0.1.0` only after at least a 14-day beta soak,
  no unwaived P0/P1 issue in the supported surface, and a fresh full release
  qualification run.
- Document deployment verification and rollback.
- Add bug, file-compatibility, and feature-request issue templates.
- Add a pull-request checklist for tests, documentation, screenshots, saved
  schema impact, and release-note classification.
- Add a security reporting policy.
- Run a short feature freeze while beta feedback is triaged.

### Severity model

- **P0:** Data loss, document corruption, or security vulnerability.
- **P1:** A broken core drawing, editing, save/reopen, or export workflow.
- **P2:** Serious interoperability, browser, performance, or usability issue.
- **P3:** Enhancement or new capability.

### Beta release gate

- No unwaived P0 or P1 issues in the supported beta surface. A waiver must name
  the owner, user impact, workaround, and target fix release.
- Canonical round-trip fixtures pass.
- All registered commands have lifecycle coverage.
- Supported browser smoke tests pass.
- Paper output and interoperability fixtures meet documented tolerances.
- Compatibility limitations and backup guidance are published.
- Deployment and rollback have been exercised.
- The beginner guide and starter tutorial batch are available.

## Post-beta feature order

Choose additions from observed workflows rather than the old feature list.
Suggested batches are:

1. Explode, Join, and Break.
2. Chamfer.
3. Ordinary rectangular and polar Array commands.
4. Construction lines and rays.
5. Angular, radius, and diameter dimensions.
6. Leaders and callouts.
7. Multiple sheets and reusable title-block templates.
8. Advanced accessibility, browser parity, and localization improvements beyond
   the baseline keyboard, focus, and dialog requirements for beta.

Every new command must satisfy the cross-cutting definition of done below.

## Blender and Bonsai path

Treat interoperability as an incremental program:

1. Document reliable SVG/DXF unit, origin, layer, and curve workflows.
2. Add a Nanquim export profile qualified against Blender import.
3. Publish versioned sample drawings and a Blender workflow tutorial.
4. Prototype a small importer or add-on only after the exchange profile is
   reliable.
5. Consider direct Bonsai connectivity after the Nanquim document and entity
   schemas are stable.

Parametric constraints, real-time collaboration, cloud storage, a plugin
architecture, and touch-first UI remain research topics until the core document
model reaches stability.

Persistent Undo/Redo serialization is also deferred. Pre-1.0 document changes
should instead make New/Open reset history reliably.

## Cross-cutting engineering work

These tasks support the milestones but should not displace user-facing safety
work:

- Consolidate browser-global SVG.js and npm SVG.js into one pinned runtime after
  command and browser tests protect current behavior.
- Stop adding new dependencies on undeclared globals.
- Sass imports, global functions, and retained public-asset URLs are migrated;
  next resolve mixed-import and bundle-size warnings.
- The UI and Paper export now share bundled local fonts; add bundle-size
  reporting and budgets.
- Add ESLint, a formatting check, and incremental `checkJs`/JSDoc validation
  without a repository-wide formatting rewrite.
- Continue reference-audited dead-code cleanup as new evidence appears; do not
  remove code speculatively.
- Extract pure geometry and lifecycle services from large modules incrementally
  behind tests. Do not begin with a wholesale rewrite.

## Definition of done for user-facing changes

A feature or command is complete only when the relevant items are satisfied:

- Registry name, aliases, category, description, and context are correct.
- Help content and illustration are present or explicitly unaffected.
- Pointer and typed input paths behave consistently.
- New geometry uses the active destination and expected inherited style.
- Helpers are visible, non-persistent, and removed on completion/cancellation.
- Terminal prompts and typed values are recorded clearly.
- Undo/Redo and redo invalidation are correct.
- Selection, Outliner, Properties, and spatial indexes update correctly.
- Save/reopen preserves the feature's semantic state.
- SVG, DXF, and Paper export effects are tested or documented as unsupported.
- Unit/integration tests pass; browser-visible changes receive a real-browser
  check.
- Accessibility, documentation, sample, and tutorial impact are reviewed.
- No unrelated production assets, generated output, or build warnings are
  introduced.
